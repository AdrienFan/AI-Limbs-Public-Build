# Plugin and child-extension source policy

Every installable `.ailp` and `.ailx` must point to a recoverable source revision. This applies to parent plugins, child extensions, and releases built outside the primary development machine.

1. **Commit first.** Build from a clean, pushed Git commit. Record the repository, complete commit SHA, package ID, manifest version, module version, signing identity, and GitHub Actions run URL. A local-only binary is a development fixture and must not be distributed as a release. APK timestamps and version strings do not identify source.
2. **Keep versions aligned.** A package's `plugin.json` or `extension.json` version must equal its module's `versionName`. A changed installable package gets a new version; do not publish different bits under an existing version. The CI source check covers every manifest under `plugin-lab/packages/`.
3. **Attach proof to the binary.** After signing, run `python3 tools/plugin_lab/source_provenance.py record --manifest plugin-lab/packages/<slug>/<plugin.json|extension.json> --package dist/<name>.ailp` (use `.ailx` for a child). Ship the resulting `.source.json` with the signed package and SHA-256 checksum. The receipt binds the package and payload hashes to the exact source commit. An Actions artifact is temporary and is not a release archive.
4. **Preserve the revision.** After a successful build and before making it available for installation, create a protected source tag `source/<slug>/v<version>` at the receipt's commit and attach the package, checksum, and receipt to a durable GitHub Release. Do not move an existing source tag. Keep the tag even when branches and temporary artifacts are deleted. A replacement build needs a new version and tag.
5. **Record base compatibility.** The release description names the tested Host build, package signing identity, required parent plugin, migration notes, and whether this is a fresh install or an in-place update. A base APK and a dynamically installed plugin are separate artifacts; each must identify its own source commit.
6. **Recover from a lost source.** If only an APK or `.ailx` remains, mark that version `source unavailable`. Do not claim decompiled output is original source. Start a new version from a verifiable commit, compare behavior, and retain the old package and user data until the replacement has been tested.

Run `python3 tools/plugin_lab/source_provenance.py check` before each cloud build. The CI inventory includes each manifest and module, their matching versions, the exact checkout SHA, the proposed source tag, and the run URL. Source tags and releases are a separate publish step after the cloud build succeeds; a green build alone does not authorize installation.
