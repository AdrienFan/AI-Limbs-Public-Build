# build43：修复 Core 启动期通信端口选择

## 本轮证据

build42 / versionCode 115 在开启 Resident 后报告 `Core did not become ready`。Core 日志显示依赖预检成功，进程阶段 running、业务阶段 detached；尚未进入插件进程启动阶段，因此本次日志不能验证 build42 的插件启动互斥修复。

Core 持有 bootstrap.lock，固定端口被旧监听占用，本次启动已发布独立的 active.socket。直接读取本次端口的 status 响应约 20 毫秒，返回 available=true、phase=running，权限后端为 ready。对旧固定端口的只读 status 请求在两秒诊断上限内未得到响应。诊断没有停止进程或触发业务接管。

## 原因与修复

源码存在一个可造成就绪误判的启动窗口：Core 先持有 bootstrap.lock，之后初始化并公布 active.socket。Host 在此期间认为 Core 已存在，但端口选择仍指向旧固定端口，等待旧监听会占用六秒就绪检测预算。端口已经发布后的 IO 错误也会再次导向旧端口。实机端口对比确认了旧监听阻塞与新端口可用；本轮没有采集失败发生瞬间的每次 socket 调用轨迹。

- 当前启动存在 launch.request 但尚未公布端口时，立即报告等待端口发布，由现有就绪循环继续查询。
- 公布端口后，将其作为该次启动唯一的控制端口；非法公布内容明确报告错误。
- 使用原子 rename 公布端口，避免删除旧文件再重命名之间的空窗。
- 保留既有旧版 Core 未公布端口且没有新启动请求时的固定地址兼容。
- 就绪超时报错增加最后一次 status 结果，以保留通信失败原因，而不只附上 Core 的启动日志尾部。

不修改 Core / Host / 插件进程分工、权限交接、业务接管顺序、门禁和重启逻辑。保持 build42 的插件生命周期互斥修复。

## 验证与交付

已完成现有进程的只读端口诊断和租约核对。源码检查覆盖未公布、有效公布、无效公布、旧版端口兼容及超时诊断路径，提交前执行 Git 差异检查。

候选版本 `0.8.0.5-build43` / versionCode 116，沿用当前分支的稳定包名与签名配置。推送后触发 GitHub Android 构建，不监控构建进度。

本轮不执行本地编译或测试。新 APK 的开启 Resident、Host 重启、插件展示及安装仍需实机复测；对旧 APK 的端口诊断不代表新版本已通过端到端验证。
